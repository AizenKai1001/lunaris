# Dogfooding Lunaris: building "Depths", a whole small game, with only the engine's tools

The question was "how close is this to a fully usable game engine?". The honest answer before this exercise was: nobody has built a complete game with it, only small
examples. So one complete game was built end to end (a top-down dungeon crawler: three generated levels, menus, pause, game over and win screens, saved games, music,
a conversation, two languages, an export) using only the tool API, text data and Lunaris Script, and **every time the engine got in the way it was written down here**:
fixed when small (with a test), documented when big. This is the honest list, not a success story.

The game is `examples/depths/` (scenes, art, sound, language files, `shots/`), made by `tools/build_depths.py` (art `tools/make_depths_art.py`, sound
`tools/make_depths_audio.py`, playtests `tools/make_depths_tests.py` into `examples/tests/depths_*.test.json`, pictures `tools/depths_shots.py`, export proof
`tools/check_depths_export.py`). `docs/GAMES.md` ("A fifth game: Depths") says how it plays and which patterns in it are worth copying.

## Second pass: the gaps that were left

A second helper went back to the "Not fixed" rows of the table and fixed them in the engine, each with tests and docs, one commit for each (E1 to E6 in the last column of the table): E1 `87426f3` draw order (12), E2 `1226560` language switch (20), E3 `94d01ca` menus and scene switches (19, 16, 17), E4 `af70777` `tilemap_colliders` numbers and missing scene paths (15, 18), E5 `b1b09e7` the interface on other screens (21), E6 `613afbd` the headless self-test player (26) and the design note on lit sprites (27). Every one is a **new component or new resource name**, so no existing scene changed: `tools/golden_hashes.txt` still matches on Linux for 42 of its 43 lines (the 43rd is the village frame hash of row 25, which was already wrong there) and all 36 playtests pass. What is still open from the table: 22 (what a `call` step can read in a playtest), 25 (the village frame hash), 27 (lit sprites, a design note below), 28 (documented behaviour).

## What was easy

- **A level in one call.** `generate_map` + `autotile` + `tilemap_colliders` gave a connected, solid, drawn level with a start, an exit and spread-out spawn points; three different generators (rooms, caves, a maze) needed only a different `mode`. The only level logic written by hand is the door (a chokepoint cell found by trying each cell of the way) and the key (far from the start and the door).
- **Guards.** `Sensor` with line of sight and `Steer.seek` worked the first time: a guard sees the hero across a room, not through a wall, runs at it, loses interest after a few seconds. Bats (no line of sight, faster) were a parameter set.
- **Menus.** `Ui` + `UiStyle` + `TextFont` + `UiNav` + `InputMap` gave a title screen that works with keys, a pad and the mouse and looks good with no art. The Dialogue copied from the village worked unchanged.
- **Scene switching, saving, fading.** `SceneSwitch` + `ColorGrade.fade` + `game.save` / `game.load` did what they say.
- **Effects.** `ParticleModules` torches, the sparkle and death clouds restarted by `Particles.time = 0`, bloom and a vignette from `Environment`: a few lines each.
- **Tests as data.** `verify` with `until` made the bots independent of exact timing (hold a key until the hero's x reaches a cell); `replay_check` caught two real engine faults (8 and 9). A bot that plays the whole game, title to win screen, is one 400-step JSON file made from the scenes.
- **Export.** One command, 22 files, and the exported folder, started with a scripted Enter press, plays the same game tick for tick as the workspace.
- **Building and running on a separate Linux test machine** (copy the tree, build, run) was reliable; `serve` over stdin made a build script and a debugging probe the same kind of program.

## What was painful

- **Not seeing the game.** Everything is a still picture or a number: to know whether a guard hunts or a door blocks you have to build a probe. About a quarter of the calls were probes (`get`, `render` with `visible`, `contacts`).
- **The two bugs that looked like "nothing happens"** (7 and 12): an invisible hero and guards that never bite had causes (a camera tilt, a z drift) that no tool pointed at; both are `check` rules now.
- **Fields and defaults.** The schema lists fields but not what each default does to a 2D game (the CameraRig's tilt, `HitPoints.hurt` starting at 100, `UiNav` focusing nothing); I read the source several times (scene switching, the export, the player, `UiNav`) to be sure.
- **Scene switching has sharp edges** (16, 17): the first design (persistent hero and music) did not survive them.
- **Every engine fix costs a two minute release build** on a Linux test machine, so the cheap loop is the Python one; engine fixes were batched.

## What is still missing for a game like this to ship

- A settings screen (volume sliders on `bus.NAME.volume` are easy, key rebinding is not there), several save slots in a menu, and a language menu (the switch itself is there, 20).
- 2D lighting (27), animated tiles, nine-slice panels (UI that keeps its shape on other screens is there now, 21).
- A windows export that was run on Windows: only the Linux export was proved here (the PC was left alone); installers, icons, a window title.
- Sound made by hand: the music is arithmetic (`make_depths_audio.py`) and good for testing, not for release. No voice, no mix by ear.
- Content: the game is ten minutes long as designed (three levels), the guards are simple, and a bot that only walks the shortest way survives all three levels with the guards alive, so the balance needs a person to play it.
- A way to look at the running game from outside (a streamed picture), which would have saved a quarter of the work (the headless self-test player, 26, is there now).

## Design note: lit sprites (gap 27, investigated and not implemented)

**What is there.** A sprite and a tile map are drawn **unlit**: the reference renderer's `Shade::Sprite` (`raster_triangle` in `crates/lunaris-render/src/render.rs`) and the GPU's `fs_sprite` (`crates/lunaris-gpu/src/shaders/scene.wgsl`) both return `colour * texel` and blend it, with no normal, no light and no shadow. Meshes are lit by `shade_lit` (an ambient of 0.16, up to 16 lights from `Scene::lights`, a point light's falloff `(1 - (d / range)^2)^2`, a Blinn-Phong highlight) and in the GPU's high qualities by a PBR path with shadow maps. Both renderers already receive the same `Scene` (`gather_scene`), whose `lights` list holds every `Light` of the world, so what a sprite needs to be lit is already in the data both draw from.

**The smallest design that fits the engine's rules** (a picture-only feature that opts in and changes no existing picture or hash):

1. A new component `SpriteLit {ambient: f32, strength: f32}` beside a `Sprite` or `Tilemap` (new, so nothing existing changes; the same idea as `DrawLayer` and `UiScale`). Without it nothing is lit, as today.
2. The light of a sprite is **flat**: its normal is the one the quad has, +z towards the camera, so a point light at height `z > 0` over the plane lights it by `max(dot(n, l), 0) * attenuation` (a light at the sprite's own height lights nothing, a light a metre above it makes a disc of light, a spot makes a cone), the sun lights it by its angle. That is the classic "2D light is a 3D light above the picture" model and needs no normal map. The result multiplies the sprite's colour before blending: `colour * (ambient + strength * sum of the lights)`, so translucent sprites, tile maps and the `DrawLayer` order are untouched.
3. **Reference renderer**: `Shade::Sprite` gets `lit: Option<(f32, f32)>` and the light list, and shades per pixel from the interpolated world position (`Vtx::world` is already computed for sprites). **GPU**: `ObjectData.mat` of a layer is unused (`[0.0; 4]`), so `mat.xy` carries `(ambient, strength)`; `vs_sprite` passes the world position on and `fs_sprite` loops over `frame.lights` as the mesh shader does (the lights are already in the scene bind group). Both use the same formula in the same colour space (the classic mode's gamma 2 working space), so `crates/lunaris-gpu/tests/compare.rs` can compare them like every other picture.
4. About 150 to 200 lines in all (the component and `check`, the gather, the two shaders, tests that compare the two renderers and the old picture with `SpriteLit` absent), so it fits the size of the other second-pass items. It was left out only for time.

**What it does not give, and the next steps.** No shadows: a wall does not stop a torch's light (that needs occluders: the `Collider`s of the world are what a 2D game would use, as a shadow-casting 2D light does in other engines; a ray per pixel is too dear, a polygon of the light's visibility per light is not, but it is a feature of its own). No normal maps (a `normal` texture beside the sprite's picture would give relief). Particles stay unlit (the additive glow of a torch is a sprite or a cloud, which is how the game does it now). Until then the game's way, a big dark sprite with a transparent middle that follows the hero plus additive clouds for torch glow, is the right tool: it is free and the same in both renderers.
